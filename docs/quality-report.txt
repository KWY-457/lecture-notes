# 1. 三个缺陷分别是什么

用户报的原话是三条：录音环境稍嘈杂就识别错误；总结重点仅仅是概括；还容易出现不明字符。
诊断之后，真凶和表象不完全是一回事，这点很重要：

用户看到的现象 | 实际病根 | 修法
嘈杂就识别错 | 抗噪前端只有「去直流 + 95Hz 高通 + 峰值归一」，既没降噪也没语音检测；纯噪声段被原样丢给 Whisper，模型听不清就编 | 新建纯 JS 谱减 + VAD 前端

# 2. 缺陷①：嘈杂录音识别错 —— 新建抗噪前端

## 2.1 做了什么

新增 public/denoise.js（纯 JavaScript，零依赖，无 WASM）。这不是随手加的滤波器，是一个完整的 STFT 降噪前端：
512 点汉宁窗、75% 重叠（32ms 帧 / 8ms 步进），迭代式 radix-2 FFT，原地运算
每频点噪声底追踪器：能量低于估计就快速跟下、高于估计就缓慢上爬（不对称是关键，对称追踪会把老师讲课的谐波当成噪声底学走，人声被削没）
增益用 Ephraim-Malah 决策指向法（先验信噪比平滑系数 0.94）
自适应过减：按信噪比在 1.0~1.3 之间调过减系数
VAD 用 Otsu 直方图判阈（不是全局分位数 —— 那条路会把纯噪声段判成语音），门限包络起音快（约 2 帧 / 32ms）、释放慢（约 8 帧 / 128ms）
工频嗡陷波：只做检测，不盲陷；抛物线插值定位峰值频率；两道闸门（跨帧稳定性 + 相对响度）拦假检出
两道保护：稳态音调保护（单个频点占据语音频段一半以上能量时跳过谱减 —— 数学上无法判断它是噪声还是信号）、增益下限（不把频点掐死，避免「水声」）
两个刻意的设计约束（改动这个模块时必须守住）：
不改变样本数量。整条音频时间轴一动不动，所以 [mm:ss] 时间戳、音频跳转、SRT 全都还对得上。实测 864000 样本→864000 样本。
非语音段是「压低」不是「删掉」（压到 -22dB）。留底让 Whisper 的分块边界仍落在自然停顿上，不会切碎语音。

## 2.2 验证数字（合成夹具，54 秒，23 句发言 22 处停顿）

指标 | 数值 | 判据
停顿段底噪 | -36.0 → -51.5 dB（降 15.5 dB） | ≥12 dB
语音电平损失 | 0.7 dB | ≤2 dB
纯噪声段 | -30.8 → -54.2 dB（降 23.4 dB） | ≥12 dB
50Hz 工频嗡 | -30.3 → -43.5 dB（降 13.1 dB，检出 53.3Hz） | ≥12 dB
满语音录音电平损失 | 0.7 dB | ≤6 dB
对数谱失真（听感口径） | 6.7 dB，不降噪的基线是 7.3 dB | ≤基线+1.5
干净录音谱失真 | 2.7 dB（回抬 0.0 dB，即没被动过） | ≤6 dB
1kHz 稳态纯音 | 损失 0.0 dB（保护生效） | ≤6 dB
处理成本 | 248 ms / 54 秒音频（≥10 倍实时） | —

关于谱失真这一项要说清楚：单独一个「<6dB」的阈值是量错了对象。宽带噪声本身的随机起伏就值 6~7dB。降完 6.7 dB 比不降噪的 7.3 dB 更接近干净信号，这才是正确的判据，所以测试改成跟基线比。

## 2.3 接进主链路的顺序（这里踩过一个坑）

原来的处理顺序是「解码 → 高通 → 归一化」，抗噪如果加在后面，95Hz 高通会先把 50Hz 工频嗡抹掉，陷波器就再也找不到目标。
改成的固定顺序是：
解码 → 抗噪（先看原始频谱）→ 高通 + 归一化 → 交给 Whisper

## 2.4 产品化行为（tests/test-pipeline.mjs 24/0）

体检分 ≥70 且信噪比 ≥25dB 的录音直接跳过，一个样本都不动（干净录音不该被无谓处理）
设置里可以关掉（asr.denoise: false）
进度条会如实报：「抗噪完成（248ms）：底噪 -29 → -46dB（降 17dB），说话段占比 48%，压掉 53Hz 的稳态嗡声。音频长度未变，时间轴照旧。」
抗噪记录随转写一起存进 transcript.json 的 denoise 字段（服务端白名单已放行），界面上会显示「已抗噪（底噪降 N dB）」
踩过的坑（值得记住）：这个「底噪降了多少」的数字一开始报出「-5dB」（不降反升），因为用逐帧频段能量的 10 分位当底噪，跟 RMS 不是一个量纲。改成在时域上量最低能量那 20% 帧的 RMS，并且必须在任何处理之前先量一次（后面全是原地改数据，等结尾再量「处理前」量到的已经是处理后的了）。

# 3. 缺陷②：不明字符 —— 真凶不是乱码，是繁体字

## 3.1 先推翻一个假设

最初的假设是「编码垃圾/乱码字符」。写脚本逐码位扫描三条真实记录后，这个假设被推翻了：

类别 | 出现次数
半角片假名 U+FF61–FF9F | 0
注音符号 U+3100–U+312F | 0
emoji | 0
私用区字符 | 0
CJK 兼容汉字 U+FA00–FAFF | 0
日文假名 / 谚文 | 0
全角括号（Whisper 自己加的注释） | 21 个（成对，有意义，保留）

非正文字符一个都没有。 用户说的「不明字符」，实际是繁简混排（476 个繁体字，占全部 29860 字的 1.6%）加上 Whisper 的用词幻觉。
所以修法不是「拼命扩删字符正则」，而是「统一繁简」+「白名单兜底」。

## 3.2 繁→简表换代

旧表是手写的，实际只有 195 条，其中 23 条是自己映射自己的废条目（呢:呢 音:音 源:源……），真正干活的是 169 条。
拿它去处理真实记录，硬数字是这样的：

指标 | 数字
OpenCC 认定的繁体形总数 | 2965
旧表认得且结果相同的 | 169（5.7%）
旧表漏掉的 | 2796（94.3%）
旧表在三条真实记录上实际能处理的繁体形 | 0 个
真实记录里实际存在的繁体形 | 476 个
新表能处理的 | 476 个（100%）

换表的代价：表从 0 行变成 19,083 字节。选择打成一个 FLAT 字符串（每 2 个字符一组 [繁,简]）+ 一个 Map，这是零依赖项目里最省事的做法。
只收单字 1:1 映射是刻意的：长度严格不变，所以逐段时间轴不会被破坏。
只做字形转换、不做词汇转换也是刻意的：「計程車」会变成「计程车」而不是「出租车」—— 字形转换不该改老师的用词。这一条在文件头注释里写清楚了。

## 3.3 清洗策略：从黑名单改成白名单

旧代码是「删掉这些 Unicode 区段里的字符」，漏一个区就漏一类字符。改成白名单：只保留正文码位，其余一律丢弃。
顺带修的三件事：
全角 ASCII 能救回来：「ＡＢＣ１２３」→「ABC123」（顺序必须在白名单之前）
康熙部首做 NFKC 归一：「⾔」→「言」（这是能救回正文的）
括号注释保留（记录里那 21 个全角括号是有意义的注记）

# 4. 顺带查出的关键 bug：大模型校对一直是坏的

## 4.1 校对从没跑起来过

两条真实转写的 cleanedBy 都是 rule，说明大模型校对从未生效。原因是 127.0.0.1:8080 上没有服务在跑 —— 代码和配置一直都是对的，只是服务没起来。
现在已拉起（命令和参数见 §9.1），实测校对可用。

## 4.2 跑起来之后撞上的真 bug：输出被截断成半截 JSON

第一次实跑 88 分钟那条（413 段）到第 5 块时崩了：
Error: 大模型校对输出不是合法 JSON，请重试
病根：校对要求模型逐条回抄原文，输出长度和输入同量级；而服务端转发时从不传 max_tokens，llama-server 默认 -n_predict 512，输出被硬截断成半截 JSON。
修的四处：
public/llm.js 的 callLLM 新增 maxTokens / timeoutMs 参数并透传
server.mjs 的 POST /api/llm 转发 max_tokens，超时改为可覆盖，并回传 finish_reason
新增 salvageJsonArray(text)：用括号配对 + 字符串状态机，把被截断的 JSON 数组里已经写完整的对象抢救出来
校对链路重写成逐级降级：块大小按 5000 → 2500 → 1250 → 800 逐级重试；只有整个块的条目数一条不差才采纳（少一条就是丢一段逐字稿）；全部失败则整块回退确定性清洗结果，绝不缺段
界面上的表现：万一某块降级了，会明确提示「第 2、3 块大模型没交出完整结果，已按基础清洗保留（未校对）」，而不是静默吞掉。

## 4.3 验证

test-proofread-robust.mjs 37/0：用伪造的接口分别模拟「正常 / 输出被截断 / 裹着代码块 / 彻底不是 JSON / 模型报错 / 只回一半条目」六种情况，每一种都做到段数守恒、无空段、时间戳原样保留。
真实复跑 88 分钟那条 413 段：5/5 块全部完成，没有降级块；段数 413→413、时间戳未变、无空段；字数 20593→20552；耗时 436 秒。
核对音近错字：「鸡疫」0 次 /「基因」2 次；「设夺」0 次 /「设备」3 次。
但要如实说：只有 20/413 段被改动 —— 因为 whisper-small 转得太烂，大模型也改不动。这不是校对功能的问题，是上游转写质量的问题，也再次说明 §8.1 的重转写是必须做的。

# 5. 缺陷③：总结太浅 —— 提示词重写

## 5.1 病根

系统提示词写着「你只依据给定的材料整理，不编造内容」。要求它不推理，它当然只能做缩句和换说法 —— 产出必然是「压缩版逐字稿」。

## 5.2 重写的思路

改成两段式：
MAP（分段）：既要讲解也要摘录。允许补背景知识，但必须带「（补充）」标记；绝不允许编造老师没说过的结论、数字、例题
REDUCE / DIRECT（成稿）：新增两个小节 —— 「理解脉络」（3-8 条把知识连成一条线：要解决什么问题 → 前人做法卡在哪 → 这节课怎么绕过去 → 概念间关系）和 「易错与易混」（写成「X 和 Y 的区别在于…」）
短课走独立的 DIRECT_PROMPT / DIRECT_SYSTEM，因为它的输入是原始逐字稿（老师通常只讲了「是什么」没讲「为什么」），必须显式授权模型去解释和补背景；而 REDUCE 的输入是已经带讲解的分段要点。

## 5.3 调优过程中撞出来的四个坑（都值得记住）

提示词里的圆括号说明会被模型当成正文抄进来。A/B 测出「理解脉络」440 字看起来达标，打出来一看 300 多字是提示词本身（"2-3 句，说清内容与它在整节课里的位置"）。
→ 修法：所有写作要求从 （…） 改成 ［…］，并在模板开头加一句「方括号里的话是给你的写作要求，不是要写的内容 —— 绝对不要把它们抄进输出」。
→ 教训：绝对不要在给模型的提示词里用圆括号写说明。
→ （2026-10-15 追加教训）这个修法不彻底：老大第二轮实测发现，改成全角方括号后模型照样把「［40 字以内，说清这节课的主线。］」「［这是整份笔记的核心…］」整段抄进笔记正文（1305e386 的 note.json 实锤，generator='offline' 的旧笔记里就有）。所以光靠提示词请求是不够的，必须代码兜底：新增 stripPromptLeaks(md)，把「［…］」整段（可跨行）在渲染入口和保存前各过滤一次，见 §13。
句式范例被当模板照抄：要求写成「X 和 Y 的区别在于…」，模型直接输出了带字面占位符的句子。改用「概念甲」「概念乙」占位，并明写「不许把占位符写进输出」。
整句照搬：120 段样本上重合率 73.9%，模型把逐字稿整句搬进「课堂脉络与重点」。
→ 加硬性要求「除专业术语、公式、专有名词和数字外一律用自己的话重写，每条要点概括成 20-40 字」。
阈值定标返工两次：「理解脉络 ≥300 字」这条硬阈值在 2400 字的材料上根本达不到，只会得到一个恒红的测试 → 改成按材料长度定比例（max(150, 材料字数 × 8%)）；「新版产出更厚」也从硬断言降级为只提示（同一条记录三次跑出 4618 / 4937 / 6296 字，采样方差太大）。

120 | 7211 | 12056 | 213 | 158 | 9 | 72.5% | 23.9s
137 | 8423 | 15859 | 321 | 217 | 10 | 65.3% | 50.3s
137 | 8423 | 16070 | 204 | 163 | 10 | 65.6% | 50.0s

修正后的结论是三条：
「理解脉络」不随材料长度增长（188～321 字之间波动，同一条 8423 字材料两次跑出 321 和 204），但长稿也写得厚——「拐点之后塌到写不长」不成立。
真正的病根是测试门槛设错了：test-ainote-depth 按材料长度定比例门槛（max(150, 字数 × 8%)）。2398 字材料只要求 192 字，能过（实测 215～250）；而 5000～9000 字的材料按 8% 要 426～674 字，模型实际只能写 188～321 字——按比例钉死 = 长稿恒红。所以这不是「深度天花板」，是「门槛和模型行为不匹配」。
给产品化的结论：深度门槛只能钉绝对下限（150～200 字），不能按比例；想在中长稿上拿到真正的深度，要靠分段独立生成这几节或换更强的模型——不是调提示词能解决的。test-ainote-depth 默认 MAX_SEG=40（即 2398 字材料）所以稳定通过；它测的是下限保底，不是长稿深度。

# 6. 新增：连云端 API（给配置不行的电脑留一条路）

## 6.1 为什么要做

本机跑 large-v3-turbo 要 1GB 权重 + 显存/内存，7B 笔记模型常驻还要 6GB 左右显存。买家未必有这个配置：跑不动，或者跑起来整台电脑卡。所以除了「本地」，必须让人能选「云端」。
云端不是简单地「加个 API Key 输入框」——那样做出来的是个玩具，因为买家不知道去哪申请、填哪个地址、填哪个模型名。所以这一块做的是一份带教程的服务商清单。

## 6.2 做了什么

文件 | 作用
public/providers.js | 服务商注册表：地址、默认模型、价格量级、申请入口、分步 setup。前后端共用同一份（浏览器直接 import，服务端 import 后由 GET /api/providers 给出）
public/api-tutorial.md | 界面里点「怎么配」弹出来的教程（3596 字节），跟软件一起发出去，改文案不用动代码
docs/API接入教程.md | 同一份教程的完整版（20052 字节），给买家自己看或打印
resolveAsrTarget() / resolveLlmTarget() | 把「服务商 id + 用户填的覆盖项」解析成真正要请求的 {url, model, apiKey, verbose}，本地/云端在这一处分流

界面上的配套：
转写引擎多了「服务商」下拉（本地 / 硅基流动 / Groq / OpenAI / 自定义…），手动切换时把接口地址和模型名直接填进输入框，并在下面一行写清「接口：… 默认模型：… 申请地址：…」
两处「怎么配」按钮，分别只显示「转写」或「笔记」那一段教程 —— 不让用户在一屏十家里找自己那家
「清掉已保存的 Key」按钮（空字符串在服务端表示「不修改」，没有这个按钮用户就删不掉自己粘错的 Key）

## 6.3 顺手堵掉的三个坑

Key 不进不出。GET /config 只回 hasApiKey: true/false，从不回明文；PUT 的返回体里也没有。
不允许请求体覆盖凭据。原 transcribeViaApi 接受请求体里的 opts.apiKey || a.apiKey、opts.model || a.model —— 请求体是客户端说了算的，等于把用户保存的 Key 交出去（局域网里的恶意页面就能薅）。已改成只用服务端存的配置。
写盘失败不再假装成功。saveConfig 改成「先落盘、成了才改内存」，写不进去就回 500 并在界面上说清楚 —— 否则界面显示「已保存」、重启后又变回去，用户完全不知道发生过什么。

## 6.4 验证

tests/test-providers.mjs 45/0（注册表与目标解析的纯逻辑）、tests/test-cloud-e2e.mjs 29/0（真的起一个服务，走 HTTP 验配置读写、Key 保护、checkOnly 配置自检不会真发请求）、tests/dom-app-test.mjs 52/0（跑真的 public/app.js，验下拉切换会填地址、教程弹窗能出正文、清 Key 按钮真的发请求）。

# 7. 缺陷④：「转写一直在等待」—— 不是慢，是没有反馈；真凶是显存被本地大模型吃满

这一条是买家（老大）真实用的时候报上来的，比前三个缺陷更致命：它在界面上看起来像死机。

## 7.1 现象

界面上从第 1 秒到第 456 秒只有同一句「转写中 0:00 / 38:59 · 已等待 456 秒（正在下载或计算，别关窗口）」，一个字都没变，进度条纹丝不动。用户唯一的判断依据是「等」，而没有任何证据说明程序还活着。

## 7.2 为什么看着像死机：两处「没有反馈」

模型命中缓存时，下载进度一条都不报。public/worker-asr.js 的 progress_callback 只在真正走网络下载时报（判据是 p.status === 'progress' && p.file）。第二次以后模型已在缓存里，这条回调永远不会触发；而 ONNX 图编译 + 第一段推理这段时间 worker 也不发消息。
界面只有「阶段名 + 等待秒数」，没有活着的迹象。
采样证明程序确实在算：renderer 6 秒里新增 CPU 1.58 秒、GPU 进程 1.14 秒 —— 「在算，但不是死机」。

## 7.3 真凶：显存被本地大模型吃满，Whisper 上不了显卡

nvidia-smi --query-gpu=memory.used,memory.free,utilization.gpu --format=csv,noheader
→ 6779 MiB 已用 / 只剩 1121 MiB 空闲 / GPU 占用 7%
本地大模型（llama-server，约 4.3GB 的 Qwen2.5-7B）常驻占着显存。Whisper large-v3-turbo 的 q8 权重要 1.0–1.2GB，加上 WebGPU 的计算缓冲需要约 3–4GB 才稳；只剩 1.1GB 时它就在显存和内存之间来回倒腾 —— 表现就是 GPU 占用只有 7%、CPU 单核跑满、慢到看不出在动。
这也解释了为什么「配置是对的、显卡也是好的，但就是慢」。

## 7.4 修法一：让程序会说话（心跳 + 分段 + ETA）

改动 | 文件 | 作用
心跳 beat(from, stage) / stopBeat() | public/worker-asr.js | 每个阶段立刻先发一句，之后每秒一条带「已 N 秒」的进度；20 秒后补「这一阶段没有细进度，不是卡死」，60 秒后补「真的没卡死，但慢就是慢；嫌慢可以换更小的模型或改用云端接口」
第一段切到 ≤120 秒（FIRST_SLICE_SEC），之后每段 300 秒 | 同上 | 让第一个字早点出来，而不是等整条
每段报告「第 i/N 段（音频 mm:ss 起）/ 已完成 X / 用时 Y / 大约还要 Z」 | 同上 | ETA 只在跑完第一段后才给，没算完绝不编数字
阶段徽章 + 百分比 + 细说明 + 无数值时的来回爬动画 | public/index.html、public/app.css、public/app.js | 分不清「在算」还是「卡死」的问题，从界面上根除
子阶段百分比换算成总进度（overallPct） | public/app.js | 避免「下载到 100% 又跌回 0%」这种更吓人的跳动

顺手修掉一个浪费：旧代码在 WebGPU 初始化失败时会把 3 个模型源各试一遍（本地代理 → hf-mirror → huggingface.co），三次都败在与「源」无关的设备错误上。现在拆成 probeHosts() + buildOnce()，并加 isDeviceFailure() 判断 —— 只有真的像设备错误才降级到 CPU(WASM)，且降级仍用同一个源；网络/模型名这类错误直接报出来，不假装降级。

## 7.5 修法二：转写前自动腾显存（老大选的方案）

新增 const VRAM_NEED_MB = 2500;（能稳稳跑起 turbo 的余量）与 async function freeVramForTranscribe(gpu)：
显存不够且本地大模型在跑 → 说一句「显存只剩 X，正在自动停掉本地大模型腾地方…」
调接口停掉它，然后轮询等显存回来（500ms × 30 次 = 最多 15 秒）
腾够了 → 转写，并在转写结束后自动把大模型拉回来（ensureLocalLLM()，只拉一次）
没腾够 → 照样往下走，但明确警告可能退回 CPU 模式，绝不谎报「已释放显存」
明确不碰的情况：显存充足、大模型没在跑、读不到显存读数、接口挂了（转写该继续继续，不许被带崩）。
实测效果：停掉本地大模型后 freeMB 从 1121 MiB → 4843 MiB，转写立刻从「磨洋工」变成正常在算。

## 7.6 验证

tests/test-vram-autofree.mjs —— 28/0。除了上面的正常路径，专门覆盖了「读不到显存时不许卡死」（不许空转 15 秒）、「接口挂了不许把转写带崩」、「stop 只发一次，不许连环杀」、「停了还是不够就必须说清楚，不许编好消息」。
tests/probe-worker-progress.mjs —— 把 worker 源码里的 await import(...transformers.min.js) 换成 data: URL 假模块，用自制 self/fetch 接住，覆盖「模型下载中 / 模型已缓存（下载回调一条不报）/ WebGPU 失败回退 WASM」三种场景；断言含「转写百分比只增不减」。
tests/test-worker-device-fallback.mjs —— 14/0，断言「WebGPU 挂时管线只建 2 次、只探 1 次模型源、最终 device=wasm、降级文案含 WASM+慢」。

## 7.7 显卡检测：按钮删了，能力保留在设置里

原来的界面有一个独立「显卡自检」按钮，但老大第二轮实测报「点了没反应、没啥用」，已从主界面删除（见 §13）。但「显卡到底能不能加速」这个问题本身是真实的，检测逻辑保留并修好了：
「显卡自检」原来只查 'gpu' in navigator —— navigator.gpu 存在 ≠ 能用（拿不到适配器时旧逻辑会报成「支持」）。现在真去 requestAdapter({ powerPreference: 'high-performance' }) → 读 adapter.info（vendor/architecture）→ requestDevice()，失败时把原因原样带出来。
这个能力现在放在设置 → ④环境自检里（checkGpu() / runDiagnostics()），和 Node 版本、模型缓存等诊断项目一起跑，不再占用主界面。

## 7.9 三种跑法实测对比（同一台机器、同一条录音、同一份代码）

上面 §7.11 那个数字（120 秒音频、271.9 秒总耗时）是第一轮的；后来把「显卡加速到底有没有用」这件事查透了，又跑了两轮，结论推翻了「WebGPU 一定更快」的直觉。三轮全部是绕过界面、直接调 public/asr-local.js 的真实链路（tests/bench-real-asr.mjs，走真浏览器 CDP），测的都是 新录音 1（38:59，onnx-community/whisper-large-v3-turbo，language: zh，denoise: true）：

跑法 | 音频长度 | 转写本体 | 相对实时 | 输出质量
WebGPU + q8（量化） | 120 秒 | 526.8 秒 | 0.23× | ❌ 成段乱码（英文/俄文/日文混着蹦）
CPU(WASM) + q8（量化） | 120 秒 | 约 300 秒 | 0.40× | ✅ 中文可读
WebGPU + fp16（半精度） | 30 秒 | 46.5 秒 | 0.64× | ✅ 中文可读（最好的一档）

（同表里的第一行 526.8 秒、第二行 0.40× 是此前两轮的实测；第三行是这一轮 30 秒音频的实测，总耗时 51.2 秒 里含 整条音频解码 4.7 秒。）
由此得出一条必须记住的配置规则（已经写进代码）：
q8 量化模型不能配 WebGPU。 同一份 encoder_model_quantized.onnx / decoder_model_merged_quantized.onnx，走 WebGPU 会输出成段乱码，而且比 CPU 还慢（GPU 占用只有 13–22%）。这是 ONNX Runtime 的 WebGPU 后端对量化算子支持不成熟，不是参数没调对。
所以 public/worker-asr.js 里新加了一个 pickDtype(model, device, override)：设备是 webgpu → fp16；设备是 wasm → q8（public/asr-local.js 会把 cfg.dtype 传进 worker，cfg.dtype 也可以显式覆盖，用来复现上面那个坑）。
代价：fp16 权重单独一份，encoder_model_fp16.onnx 1215.3 MB + decoder_model_merged_fp16.onnx 328.3 MB ≈ 1.5 GB（vs 量化版 615 MB + 419.6 MB ≈ 1.0 GB），第一次用要下载。data/models 目录现在两种都在，合计 3549.9 MB。
为什么 WebGPU 也没快到哪去：这台是 NVIDIA GeForce RTX 5060 Laptop GPU、显存 8151 MiB（见 §7.3），但 Whisper 的 ONNX 图里有大量小算子，WebGPU 每个算子的提交/拷贝开销把并行优势吃掉了 —— 所以「有独显 → 一定比 CPU 快」这个直觉在这个模型 + 这个后端上不成立。真正把速度拉开的是精度（q8↔fp16）和要不要跟本地大模型抢显存，不是显卡本身。
给买家的实话：想快，按性价比排序是 ① 转写前先别开本地大模型（已自动化，见 §7.5）→ ② 显卡够就开 WebGPU + fp16（约 1.6 倍于 CPU，代价 1.5 GB 下载）→ ③ 直接买云端接口（见 §6，最省事）。录 1 小时大概要转 1 小时上下，这是 large-v3-turbo 在 8GB 笔记本上的真实水平。

## 7.10 这一轮新增的两条验证（都能复现）

tests/bench-real-asr.mjs 现在支持 --device 和 --dtype 两个开关，可以逐格复现上表：node tests/bench-real-asr.mjs --secs 30 --device webgpu --dtype fp16。

## 8.4 本地还是云端，得让买家自己选

 | 本地 | 云端
花钱 | 不花 | 按量计费（转写一小时大约几毛到几块，看服务商）

## 8.5 拼音首字母误识：提示词已修，但要在真实数据上验证

# 12. 本报告是怎么生成的

正文源文件是 docs/quality-report.md（纯手写，所有数字都来自下面这些脚本的实际输出，没有估算）。
Word 版本（docs/quality-report.docx）由一个约 200 行的转换脚本从上面的 Markdown 生成，不是手工排版的。转换过程中撞到两个排版坑，记在这里免得下次重踩：
行内代码不能改成等宽字体。第一版把反引号里的内容设成 Consolas，在没有该字体的环境里 LibreOffice 会回退到 Courier，字符度量一变，整行就冲出页面右边界。
加粗里面套的行内代码必须递归处理。第一版只在外层切一次加粗标记，于是「加粗 + 里面套一个代码片段」这种嵌套里的反引号被外层整段吞掉，渲染出来是字面带反引号的正文。
另外：判断「有没有冲出版面」必须看 PDF，不能看 PNG 预览。直接用 LibreOffice 渲染出的 PNG 会给人一种「文字被右边界裁掉」的假象，转成 PDF 再看就完全正常。这一轮是白折腾的。

# 14. 可售性判断（实话）

能卖的部分：

繁简处理现在是对的（覆盖 100%，长度守恒）
大模型校对的降级链路做得扎实（六种坏输出下逐字稿一段不丢）
提示词从「缩句」升级到「讲解 + 梳理」，短课效果明显（重合率 70.9% → 56.1%）
本地 / 云端两条路都通了，而且带教程 —— 配置差的电脑不必被劝退，也不必修好电脑才能用
界面按实测反馈改过一轮：思维导图吃 AI 结构、导出 Word 双击可开、提示词泄漏有代码兜底（§13）
不能吹的部分：
88 分钟那条录音（62b4f73d）仍是 whisper-small、读不通，在重转写之前不能拿去演示（只剩这一条；1305e386 已完成，见 §8.1）
拼音首字母误识（BJR→闭卷）的校对规则已加，但还没在真实数据上验证过（§8.5）
长课「理解脉络」不随材料长度变长，短中稿方差还大（§5.4）——不算天花板，但也别吹「多长的课都吃得住」
云端那条路要求买家自己会申请 API Key（教程写得很细，但仍是门槛）
界面上还没有「第一次用该选哪个」的引导 —— 两条路的取舍写在 §8.4，但没写进界面
建议的卖法：卖「用你的录音产出讲义」这个服务（软件当作演示），或者软件 + 一次代跑。
理由是三条真实录音的对比已经说明：同一条录音，小模型和 turbo 的产出差距是「读不通」和「能读」的区别。这一点现在虽然可以靠云端 API 绕开，但让买家自己申请 Key、自己承担按量计费，转化率会掉；代跑一次把「读不通」变成「能读」，是最直接的价值证明。
这一条是判断，不是验证过的结论。
