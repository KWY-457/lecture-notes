# 「讲义笔记」Windows 桌面化技术调研报告

> 调研对象：现状为「零依赖 Node server.mjs + 原生 JS 前端 + 浏览器 WebGPU/WebAssembly 跑 Whisper（ONNX）ASR，用户双击 start.cmd 或 Edge --app 打开」，目标改造为真正的 Windows 桌面 exe，并实现发布、自动更新、授权保护、分发。
> 数据截止：2026-10。所有版本号、体积、机制均来自官方文档 / GitHub 一手来源，见文末来源清单。

---

## 一、结论速览

**推荐组合方案：Electron（44.x）+ electron-builder（NSIS）+ electron-updater（generic provider）+ node-machine-id 机器码授权 + bytenode 字节码保护 + 自研 Range 断点续传模型下载器 + Sentry 崩溃收集 + OV 代码签名证书。**

核心依据（三条硬理由）：

1. **WebGPU 可控性**：ASR 命脉是浏览器 WebGPU/WebAssembly 跑 ONNX。Electron 自带 Chromium 152（当前稳定版 44.7.2），WebGPU 自 Chromium 113 起默认启用，行为与开发测试环境完全一致、版本可控。Tauri 依赖用户系统 WebView2：WebGPU 虽已在 WebView2 可用（2023-11 起），但 WebView2 版本跟随系统 Edge、用户环境不可控，且 2024-2025 仍有双显卡笔记本无法强制独显（#5072）、writeTexture 上传慢 1000 倍（#4468）等开放问题。
2. **Node 后端零改造**：Electron main process 原生就是 Node.js（当前 Node 24.21.0），server.mjs 几乎原样迁入。Tauri 必须走 Rust sidecar 打包 Node 运行时（官方支持但复杂度 + 体积双涨）。
3. **体积是次要矛盾**：Electron 安装包 ~70–100MB vs Tauri 3–10MB 的差距，在「模型权重几个 GB」的分发矛盾面前不构成决策要素；且 Elanis 2026-10 空壳基准显示 Tauri 内存（median 307MB）反而高于 Electron（279MB）。

**硬性限制（必须接受）**：Windows 7 无法支持本产品的 ASR 场景——Electron 22（Chromium 108，WebGPU 默认关闭）是最后支持 Win7 的版本且已于 2023-10-10 结束官方支持；Tauri 官方写「Windows 7 或更新」但 WebView2 Runtime 官方仅支持 Win10/11，Win7 上根本没有 WebView2。目标平台必须定位 **Windows 10 1809+ / Windows 11（x64）**。

### 2.2 WebGPU 专项分析（本产品最关键维度）

- **Electron**：WebGPU 在 Chrome/Edge 113+ 默认启用（[caniuse](https://caniuse.com/webgpu)）。Electron 44 自带 Chromium 152，WebGPU 早已成熟默认开启；Chromium 94–112 时代才需要 `app.commandLine.appendSwitch` 类开关（[中文博客](https://blog.glumi.cn/article/electron-enable-webgpu.html)记载的即为早期做法，现不再需要）。**版本与行为完全由我们自己控制，可 CI 实测回归。**
- **Tauri/WebView2**：官方 issue [#6381](https://github.com/tauri-apps/tauri/issues/6381)「WebGPU support?」创建当日即被关闭为 not_planned——Tauri 无法自行开启 WebGPU，完全取决于 WebView2。WebView2 侧：Construct 作者在 [discussion #4138](https://github.com/MicrosoftEdge/WebView2Feedback/discussions/4138)（2023-11）确认 "It works in WebView2 on Windows"（helloTriangle 通过），但 2024-2025 仍有开放问题：
  - [#5072](https://github.com/MicrosoftEdge/WebView2Feedback/issues/5072)（2025-01 开，2025-12 关 completed）：双显卡笔记本 Chromium 引擎默认用集成 GPU，WebGPU/WebGL 内容**无法强制独显**（NvOptimusEnablement 对 WebView2 GPU 进程无效），要求新 API ForceGPUPreference。
  - [#4468](https://github.com/MicrosoftEdge/WebView2Feedback/issues/4468)：WebGPU writeTexture 推数据 1.2s vs 纯 C CUDA 1.2ms，IPC 性能差千倍。
  - WebView2 版本随用户系统 Edge（Evergreen）漂移，测试矩阵不可控；用户/企业策略可禁用组件。
- **结论**：ASR 是重 WebGPU 计算场景，**Electron 的可控性胜出**。双显卡问题在 Electron 的 Chromium 上同样可能遇到（同源引擎），但至少可自行降级/回退并统一版本测试。

### 2.3 Node 后端集成对比

- **Electron**：main process = Node.js 运行时，`server.mjs` 可直接改造成 main 内启动（或改为函数调用走 IPC），零额外运行时、零序列化成本。
- **Tauri**：官方提供 [sidecar](https://tauri.app/zh-cn/develop/sidecar/) 机制与 [「Node.js 作为侧车进程」](https://tauri.app/zh-cn/learn/sidecar-nodejs/) 教程，属于官方认可路径；但需打包 Node 运行时（+30–50MB，抵消大部分体积优势）、管理子进程生命周期、加一层 stdio/IPC 通信，且引入 Rust 工具链（tauri 2.12.4，插件要求 Rust ≥1.90）。
- **结论**：现状就是 Node 服务，Electron 迁移成本趋近于零。

### 2.4 Windows 版本兼容性

- Electron：官方支持最新 3 个大版本，每 8 周发版（v41→Chromium 146，v42→148）；[electron-timelines.md](https://raw.githubusercontent.com/electron/electron/main/docs/tutorial/electron-timelines.md) 原文明确 "Electron temporarily extended support for Electron 22 until October 10, 2023, to support an extended end-of-life for Windows 7/8/8.1"——**Electron 22 是最后支持 Win7/8/8.1 的版本**，其后 Win7 无官方支持。
- Electron 44 breaking changes：移除 win32-ia32 与 linux-armv7l 预构建（43 系列 EOL 2027-01）、移除 macOS 12 支持、ANGLE 静态链接（[官方 breaking-changes](https://www.electronjs.org/docs/latest/breaking-changes)）。
- Tauri：前置要求页写「Windows 7 或更新」（指开发工具链），但 [WebView2 官方分发文档](https://learn.microsoft.com/zh-cn/microsoft-edge/webview2/concepts/distribution) 仅支持 Win10/11（Win11 内置、Win10 绝大多数已装），**Win7 无 WebView2，Tauri 实际无法在 Win7 运行**——这是 Tauri 文档与现实的矛盾点。
- **结论**：Win10 1809+/Win11 目标下两者皆可；Win7 场景两者都不可行（且 WebGPU 在 Electron 22 的 Chromium 108 上默认关闭，双重不可行）。

## 三、打包方案：electron-builder + NSIS

### 3.1 工具选型

| 工具 | 最新版 | 门槛 | 评价 |
|---|---|---|---|
| electron-builder | 26.15.3（npm latest） | Node ≥14 | **推荐**。NSIS 默认目标、与 electron-updater 同门、中文坑 workaround 资料最全 |
| @electron-forge/cli | 8.0.1 | Node ≥22.13 | Electron 官方维护；更新生态需自行组装，CLI 门槛更高 |
| electron-packager | — | — | 仅打包不打安装器，不满足需求 |
| tauri-cli | 随 tauri 2.12.4 | Rust ≥1.90 | 仅当选 Tauri 时使用 |

依据：electron-updater 官方文档明确 **Windows 仅 NSIS 目标支持自动更新**（Squirrel.Windows 不支持）；electron-builder 26.15.3 + electron-updater 6.8.9 是同仓库维护的组合。

### 3.2 关键配置（electron-builder）

- **代码签名**（v27 起统一为 `win.sign` 判别联合 `type: "signtool"|"hsm"|"pkcs11"|"azure"`）：CI 推荐不写配置、从环境变量 `WIN_CSC_LINK` / `WIN_CSC_KEY_PASSWORD` 发现证书。v26 用 `win.signtoolOptions`。
- **`verifyUpdateCodeSignature` 默认 true**：构建时把 publisherName 写入 app-update.yml，运行时 electron-updater 校验下载更新包的 Authenticode 签名（逐组件比对证书 Subject），防更新包被替换。自定义签名 hook 必须显式配 `publisherName`（用 `Get-AuthenticodeSignature` 从已签名 exe 取 Subject 原文），否则安装后的应用会拒绝所有后续更新。
- **更新清单强制签名（v27 起）**：`latest*.yml` 本身用 Ed25519 签名（`electron-builder create-update-key` 生成密钥，`ELECTRON_BUILDER_UPDATE_SIGN_KEY`/`_FILE` 提供），发布构建缺密钥直接失败；`updateManifest: false` 是唯一 opt-out。→ 私钥泄漏 = 可推送伪造更新清单，必须进 CI 密钥管理。
- **asar**：默认开启；`smartUnpack` 默认 true（自动解包可执行文件/原生模块）；`ordering` 参数可把首屏文件排在包前部改善启动 IO。
- **压缩**：`compression` 默认 `normal`（官方注明 `maximum` 体积收益不明显、只拖慢构建）。
- **语言包裁剪**：`electronLanguages` 只保留需要的 locale（如 `["zh-CN","en-US"]`）。
- **`requestedExecutionLevel`** 默认 `asInvoker`（当前用户安装，免 UAC 管理员权限，符合桌面小工具定位）。
- **`signExts`**：默认只签 .exe，如使用 .dll/.node 原生模块需加签。

### 3.3 中文路径/中文用户名坑（国内分发必须处理）

1. **构建机用户名/路径含中文**：makensis 在非拉丁字符 LOCALAPPDATA 下报 `Processing script file: "<stdin>" (ACP)` 乱码、nsProcess 插件找不到（[issue #2197](https://github.com/electron-userland/electron-builder/issues/2197)，西里尔用户名同因，develar 关闭，workaround=构建前把 LOCALAPPDATA 指向纯 ASCII 路径）。中文场景解法：全英文路径/用户名，或改 `NsisTarget.js` 的 executeMakensis 加 `args.push("-INPUTCHARSET","UTF8")`（[CSDN 实录](https://blog.csdn.net/wy17324808055/article/details/132827885)）。**CI 构建环境保持纯 ASCII 路径是根治方案。**
2. **安装路径禁止中文**：electron-builder 无内置限制，需自定义 NSIS 脚本（`customPageAfterChangeDir` 宏 + `PathIsDBCS_W` 逐字符判断 >128 即非 ASCII，MessageBox 提示并 Abort）——[cnblogs 完整方案](https://www.cnblogs.com/lamhoo/p/19426839)。
3. **构建时下载 winCodeSign/nsis/nsis-resources 失败**（国内网络）：从华为云镜像 [mirrors.huaweicloud.com/electron-builder-binaries/](https://mirrors.huaweicloud.com/electron-builder-binaries/) 手动缓存到 `%LOCALAPPDATA%\electron-builder\Cache`。

## 四、自动更新方案

### 4.1 推荐：electron-updater 6.8.9 + generic provider（自建静态服务器）

机制（[官方文档](https://www.electron.build/docs/features/auto-update/)）：

- 每次发布产物：`App-Setup-x.y.z.exe` + `App-Setup-x.y.z.exe.blockmap`（4KB 块差分）+ `latest.yml` 清单，全部上传到对象存储/CDN（generic 需手动上传，GitHub Releases 则自动）。
- `latest.yml` 内容：`version`、`files[]`（每文件含 `url`/`sha512`/`size`）、`path`、`sha512`、`releaseDate`。
- 差分更新：electron-updater 从 `${url}.blockmap` 下载 blockmap 按 4KB 块做二进制差分，只拉变更块（国内网络下对 70–100MB 安装包收益显著）。
- **无需自研 go-delta/bsdiff**：[go-delta README](https://github.com/balacode/go-delta) 明示对已压缩文件（asar/安装包）打 delta 收益极小，Electron 场景直接用内建 blockmap 即可。
- 灰度发布：手改 `latest.yml` 的 `stagingPercentage: 10` 即按比例放量。
- 安全链（2026 现状）：清单 Ed25519 签名（v27 强制）→ 下载包 Authenticode 签名运行时校验（publisherName）→ 安装器签名。三层防护。
- 事件 API：`error / checking-for-update / update-available / update-not-available / download-progress / update-downloaded / update-cancelled`。
- 安装时机：`autoInstallEvent` 可选 `"onQuit"`（默认）| `"onNextLaunch"` | `"manual"`。注意已知问题 [electron-builder#7807](https://github.com/electron-userland/electron-builder/issues/7807)：onQuit 模式在系统关机时安装中断，v28 计划把默认改为 onNextLaunch——**建议直接配置 onNextLaunch**（下次启动时静默安装，体验更好）。
- v27 起 `disableWebInstaller` 默认 true（不再默认产出 web installer）。
- per-machine 安装的 NSIS 更新会跳过启动自动安装（需 UAC），per-user 安装无此问题。

### 4.2 UX 惯例（「用户双击后怎么知道有新版本」）

业界标准流程：**启动时静默 `checkForUpdatesAndNotify()` → 有新版本弹系统通知/应用内横幅（含版本号与更新日志摘要）→ 用户点「下载」→ 应用内显示下载进度 → 下载完成提示「重启后生效」→ 下次启动自动安装**。支持「稍后提醒」（再次启动时重弹）。可选设置页手动「检查更新」。不要打断正在进行的录音/转写任务，仅在空闲或用户主动时安装。

### 4.3 对比：Tauri updater（仅作对照）

[v2 文档](https://v2.tauri.app/plugin/updater/) 与 [插件 README](https://raw.githubusercontent.com/tauri-apps/plugins-workspace/v2/plugins/updater/README.md)：更新**签名不可禁用**（"This cannot be disabled"）；`tauri signer generate` 生成公私钥，构建时环境变量 `TAURI_SIGNING_PRIVATE_KEY` 注入；清单为静态 JSON（`{version, notes, pub_date, platforms:{"windows-x86_64":{signature,url}}}`）或动态服务器协议（204=无更新 / 200=JSON）；Windows installMode passive 为默认推荐。功能上与 electron-updater 等价、同样有差分（zip 级），但生态成熟度和国内资料均弱于 electron-updater。

## 五、模型分发（几个 GB 权重）

### 5.1 方案决策

| 方案 | 判断 |
|---|---|
| 随安装包分发 | **不可行**。几个 GB 会让 NSIS 每次更新重传、blockmap 差分失效、首次安装体验崩溃 |
| 首次启动下载（必装模型） | **推荐主路径**。安装包只含应用（~100MB），首次启动向导下载核心小模型（如 whisper tiny/base 量化版 ~50–150MB），可选大模型按需下载 |
| 可选模型包商店 | 应用内「模型管理」页：列出可用模型（大小/精度/速度/磁盘需求），按需下载、可删除 |

### 5.2 断点续传实现（必做，行业现状反而不支持）

标准实现（[Ollama issue #13167](https://github.com/ollama/ollama/issues/13167) 讨论中给出的规范方案，参照 docker pull/aria2c）：

1. 下载前建 `.part` 临时文件，持久记录已下载字节数（含 URL + 版本标识，防止换版本续错）；
2. 请求带 `Range: bytes=N-`；服务器返回 **206 Partial Content → 追加写入**；不支持 Range（返回 200）→ 回退全量重下；
3. 指数退避重试；完成后 sha256 校验、原子改名为正式文件；
4. CDN/对象存储必须支持 Range（国内 OSS/COS/CDN 均支持），并注意流量计费。

**行业现状（教训：别照抄同行）**：

- LM Studio：官方文档确认支持 pause/resume/cancel/retry（[docs](https://lmstudio.ai/docs/bionic/models/download-local-models)）——唯一做对的主流产品；
- Ollama：**不支持**，中断后从头重下、临时文件失败即删（[#13167](https://github.com/ollama/ollama/issues/13167)、[#15320](https://github.com/ollama/ollama/issues/15320)）；
- AnythingLLM：**不支持**（[issue #4192](https://github.com/Mintplex-Labs/anything-llm/issues/4192)，2025-07 开、未关闭）。

→ 我们实现 Range 续传即构成对国产同类工具的差异化体验优势。

### 5.3 下载 UX 惯例（综合 LM Studio 等）

- 下载前明示：模型大小、所需磁盘空间（不足时阻止+提示）、预计速度；
- 进度条三要素：**进度 %、实时速度、剩余时间**；可暂停/取消/重试；
- 下载完成自动 sha256 校验，失败提示重下（不允许带病进入 ASR）；
- 首次启动向导（欢迎页 → 选模型 → 下载 → 跑通示例转写），降低挫败感；
- 模型升级：模型文件本身是压缩格式，二进制 delta 收益极低（go-delta README 明示），采用「版本清单 + 整包重下新版本」策略，不做模型增量。

## 六、授权保护

### 6.1 机器码方案

[node-machine-id](https://raw.githubusercontent.com/automation-stack/node-machine-id/master/README.md)（automation-stack 出品）：无需提权、无原生依赖；Windows 读注册表 `HKLM\SOFTWARE\Microsoft\Cryptography` 的 `MachineGuid`；macOS 读 IOPlatformUUID；Linux 读 `/var/lib/dbus/machine-id`；默认返回 sha-256 哈希（可 `machineIdSync(true)` 取原值）。

已知坑：Ghost/镜像克隆装机时同一镜像的机器 id 相同 → 授权指纹建议**组合 MachineGuid + 用户注册信息（账号）**，机器码仅作换机检测信号，不做唯一凭证。

### 6.2 激活流程（建议实现）

1. 客户端展示机器码（格式化分组便于抄写，如 `XXXX-XXXX-XXXX-XXXX`）；
2. **在线激活**：POST `{机器码, 授权码}` → 服务端校验授权码未用/可用 → 生成 license（服务端私钥签名，含 machineId/licenseId/expiry/features，RSA 或 Ed25519）→ 客户端公钥验签 + 机器码比对 → 落盘 userData；
3. **离线激活**（内网用户）：客户端导出 request 文件（机器码 + 随机 nonce）→ 用户在联网设备官网兑换 → 得到 license 文件 → 导入客户端验签；
4. 换机：服务端记录绑定、控制解绑次数或人工客服解绑；
5. 服务端持续校验：每 key 限激活次数、心跳检测多机共用、频率异常拉黑（[V2EX 社区共识方案](https://global.v2ex.co/t/931428)）。

### 6.3 防破解分层（性价比排序）

1. **架构优势（免费且最强）**：授权判定逻辑放在 Node 后端（Electron main process），前端渲染层只展示结果——社区共识指出 Electron 纯前端判断可被 DevTools 直接改掉（V2EX 帖附 gif 演示），放 main 层则天然隔离 DevTools；
2. **bytenode 1.7.0（V8 字节码，推荐）**：把 main 进程授权模块编译为 .jsc。关键版本坑（[README](https://cdn.jsdelivr.net/npm/bytenode@1.7.0/README.md)）：
   - Electron ≥42（V8 ≥14.8）主进程字节码必须用 `compileElectronMainCode()` / `compileFile({electronMain:true})`（在真实 Electron main 进程内编译），用 `ELECTRON_RUN_AS_NODE` 编出的 .jsc 会导致主进程 SIGTRAP 硬崩溃（V8 14.8 起只读快照校验和不再容错）；
   - Electron ≥43.5.1 的 preload/renderer 必须用 `electronRenderer:true` 编译（否则 cachedDataRejected）；
   - .jsc 绑定 V8 版本与进程类型、不可跨平台 → **Electron 每次升级必须重编译授权模块，纳入 CI**；
3. javascript-obfuscator 混淆辅助（前端 UI 逻辑层）；
4. asar 打包 + 代码签名（防篡改后运行，配合 verifyUpdateCodeSignature）；
5. **不推荐 VMProtect/Themida 整体加壳**：无 Electron 官方支持与社区成功先例；[Themida 官方 FAQ](https://cdnc.heyzine.com/files/uploaded/v2/698bae4256de6291dd9e8cdd7ca8f7b1502574bc.pdf) 自认 native 应用加壳后可能无法运行；ESET 有专门检测 VMProtect 壳文件的机制（[ESET 论坛](https://forum.eset.com/topic/49643-detection-of-files-protected-with-vmprotect/)）——壳化显著提高杀软误报率；且签名后改包会触发平台篡改检测（[electron-builder #5038](https://github.com/electron-userland/electron-builder/issues/5038) 的 Widevine platform_tampered 案例）。
6. 最终认知（社区共识）：**客户端无法真正防破解，攻防是性价比问题**——核心价值靠服务端校验与快速迭代，客户端防护目标是「挡住 90% 普通用户」而非对抗逆向工程师。

## 七、体积与启动速度优化

- asar 压缩 + `smartUnpack`（原生模块自动解包）；
- `electronLanguages` 裁剪语言包；
- `compression: normal`（官方说明 maximum 无体积收益只拖慢构建）；
- `ordering` 把首屏 JS/CSS 排在 asar 前部；
- 模型一律不打包（见 §5）；
- 启动优化：main 尽早 `createWindow` + 骨架屏，重模块（ASR 运行时）延迟加载；
- 参照基准：Electron 空壳启动 ≈153ms，加上应用自身加载仍有空间，属于可接受水平。

## 八、崩溃收集与用户反馈

### 8.1 方案推荐

- **Sentry（首选托管方案）**：[@sentry/electron](https://docs.sentry.io/platforms/javascript/guides/electron/)，要求 Electron ≥35；main（`@sentry/electron/main`）与每个 renderer（`@sentry/electron/renderer`）都要 init；renderer 事件经 main 转发（dsn/release/environment 在 renderer init 无效）；能力覆盖 native crash 上报、JS error、tracing、session replay（`replaysSessionSampleRate: 0.1`、`replaysOnErrorSampleRate: 1.0`）、user feedback、logs/metrics。
- **自建替代**：Electron [crashReporter API](https://www.electronjs.org/docs/latest/api/crash-reporter)（Crashpad 实现，上传协议兼容 Breakpad——任何能收 Breakpad minidump 的服务器都能收）：`crashReporter.start({submitURL, productName, uploadToServer, rateLimit, compress, extra, globalExtra})`，multipart/form-data POST（含 ver/platform/process_type/guid/upload_file_minidump 等字段）；崩溃文件存 `app.getPath('crashDumps')`；必须在 app ready 前尽早调用；`extra` key ≤39 字节、value ≤20320 字节；Node 子进程用 `process.crashReporter.getParameters()`。自建时建议：minidump 端点 + 应用日志自动打包上传。

### 8.2 用户反馈通道

内置「帮助 → 反馈」表单：自动附 app 版本/OS/GPU 信息/日志文件（脱敏），可一键发送至服务端或邮件。与 Sentry user feedback 打通。

## 十、多平台预留（未来 Mac 版）

Electron 路线天然预留充分，选型无需额外动作：

1. **同一套代码**：main/preload/renderer 全平台复用，Mac 版仅需 `mac` 打包配置 + Apple Developer 证书 + 公证（notarize）；
2. **WebGPU**：macOS 上 Electron 用 Chromium → Metal 后端，不依赖 Safari（Safari 26+ 才部分支持 WebGPU，但与我们无关）；
3. **机器码**：node-machine-id 在 mac 读 IOPlatformUUID，无需改授权架构；
4. **自动更新**：electron-updater 的 mac 目标（zip + latest-mac.yml），需 Apple 签名+公证；
5. **预留动作**（现在做，成本为零）：`appId` 用统一反向域名（`com.yourco.lecturenotes`）；所有路径走 `app.getPath()`；避免 Windows 专属 API；NSIS 定制脚本与业务逻辑隔离。
6. 反向对比：若选 Tauri，未来 Mac 版要同时维护 Rust 后端与 Node sidecar（且 sidecar 需公证），后路明显更窄。

## 十二、风险清单

| # | 风险 | 等级 | 说明与缓解 |
|---|---|---|---|
| 1 | WebGPU 在低端/双显卡设备性能不可控 | 高 | 双显卡强制独显问题（WebView2 #5072 同源）在 Electron 上也可能出现。缓解：发布前灰度实测；onnxruntime-web 提供 WASM 回退路径（CPU 推理，慢但可用），实现自动降级 |
| 2 | Win7 用户无法使用 | 中（若目标市场含 Win7 则高） | Electron 22（Chromium 108）是 Win7 最后支持版本，WebGPU 默认关闭；Tauri 因 WebView2 同样不支持 Win7。**明确产品定位 Win10 1809+/Win11**；Win7 用户仅能提供旧版 CPU/WASM 路线或放弃 |
| 3 | 32 位 Windows 无法覆盖 | 低 | Electron 44 起移除 win32-ia32 预构建。如需 32 位：锁 43.x（EOL 2027-01）。建议直接放弃 32 位（国内存量极少） |
| 4 | 中文路径坑 | 中 | 构建机中文用户名/路径、用户安装中文路径，均有 workaround（§3.3），需在产品与 CI 固化 |
| 5 | SmartScreen 警告期 | 中 | 新签名证书 + 低下载量必弹警告，EV 不消除仅缓解；靠下载量积累。缓解：官网提供「如何解除拦截」帮助页；保持高频发布积累信誉 |
| 6 | 模型下载流量成本 | 高 | 几个 GB × 用户数 = CDN 流量费用；Range 续传可减少重复流量（续传仅补差）。缓解：模型单独放 CDN 域名、按量预算、可选大模型仅向已授权用户开放 |
| 7 | bytenode 与 Electron 升级锁定 | 中 | .jsc 绑定 V8 版本，Electron 每 8 周发版 → 升级需重编译授权模块，漏编译即 SIGTRAP 崩溃。缓解：CI 强制重编译步骤 + 升级前冒烟测试 |
| 8 | 杀软误报 | 中 | 未签名/新签名阶段误报率高；切勿用 VMProtect 类壳（显著增加误报）。缓解：签名+时间戳、向主流厂商提交白名单申诉 |
| 9 | 盗版 | 低（不可消除） | 客户端防护上限明确（社区共识），靠服务端校验 + 迭代速度 + 合理定价；bytenode 挡住普通用户层面 |
| 10 | 更新私钥管理 | 高 | Ed25519 清单签名私钥（electron-builder create-update-key）与代码签名证书双密钥体系，任一泄漏 = 供应链风险。缓解：CI 密钥管理、私钥不进仓库、定期轮换 |
| 11 | electron-builder v26→v27 迁移 | 低 | v27 改动大（win.sign 判别联合、清单强制签名等），当前稳定用 26.15.3，v27 发布后按官方 `migrate-schema` 迁移 |
| 12 | 渠道效果不可控 | 低 | 华军无公开入口、商店审核周期与政策变动；官网分发为主即可对冲 |
