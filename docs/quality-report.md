## 2. 缺陷①：嘈杂录音识别错 —— 新建抗噪前端

### 2.1 做了什么

新增 `public/denoise.js`（纯 JavaScript，零依赖，无 WASM）。这不是随手加的滤波器，是一个完整的 STFT 降噪前端：

- 512 点汉宁窗、75% 重叠（32ms 帧 / 8ms 步进），迭代式 radix-2 FFT，原地运算
- 每频点噪声底追踪器：**能量低于估计就快速跟下、高于估计就缓慢上爬**（不对称是关键，对称追踪会把老师讲课的谐波当成噪声底学走，人声被削没）
- 增益用 Ephraim-Malah 决策指向法（先验信噪比平滑系数 0.94）
- 自适应过减：按信噪比在 1.0~1.3 之间调过减系数
- VAD 用 **Otsu 直方图判阈**（不是全局分位数 —— 那条路会把纯噪声段判成语音），门限包络起音快（约 2 帧 / 32ms）、释放慢（约 8 帧 / 128ms）
- 工频嗡陷波：只做检测，不盲陷；抛物线插值定位峰值频率；两道闸门（跨帧稳定性 + 相对响度）拦假检出
- 两道保护：稳态音调保护（单个频点占据语音频段一半以上能量时跳过谱减 —— 数学上无法判断它是噪声还是信号）、增益下限（不把频点掐死，避免「水声」）

**两个刻意的设计约束**（改动这个模块时必须守住）：

1. **不改变样本数量**。整条音频时间轴一动不动，所以 `[mm:ss]` 时间戳、音频跳转、SRT 全都还对得上。实测 864000 样本→864000 样本。
2. **非语音段是「压低」不是「删掉」**（压到 -22dB）。留底让 Whisper 的分块边界仍落在自然停顿上，不会切碎语音。

### 2.2 验证数字（合成夹具，54 秒，23 句发言 22 处停顿）

| 指标 | 数值 | 判据 |
| --- | --- | --- |
| 停顿段底噪 | -36.0 → -51.5 dB（**降 15.5 dB**） | ≥12 dB |
| 语音电平损失 | **0.7 dB** | ≤2 dB |
| 纯噪声段 | -30.8 → -54.2 dB（**降 23.4 dB**） | ≥12 dB |
| 50Hz 工频嗡 | -30.3 → -43.5 dB（**降 13.1 dB**，检出 53.3Hz） | ≥12 dB |
| 满语音录音电平损失 | **0.7 dB** | ≤6 dB |
| 对数谱失真（听感口径） | **6.7 dB**，不降噪的基线是 **7.3 dB** | ≤基线+1.5 |
| 干净录音谱失真 | **2.7 dB**（回抬 0.0 dB，即没被动过） | ≤6 dB |
| 1kHz 稳态纯音 | 损失 **0.0 dB**（保护生效） | ≤6 dB |
| 处理成本 | **248 ms / 54 秒音频**（≥10 倍实时） | — |

关于谱失真这一项要说清楚：**单独一个「<6dB」的阈值是量错了对象**。宽带噪声本身的随机起伏就值 6~7dB。降完 6.7 dB 比不降噪的 7.3 dB 更接近干净信号，这才是正确的判据，所以测试改成跟基线比。

### 2.3 接进主链路的顺序（这里踩过一个坑）

原来的处理顺序是「解码 → 高通 → 归一化」，抗噪如果加在后面，**95Hz 高通会先把 50Hz 工频嗡抹掉，陷波器就再也找不到目标**。

改成的固定顺序是：

```
解码 → 抗噪（先看原始频谱）→ 高通 + 归一化 → 交给 Whisper
```

### 2.4 产品化行为（`tests/test-pipeline.mjs` 24/0）

- **体检分 ≥70 且信噪比 ≥25dB 的录音直接跳过**，一个样本都不动（干净录音不该被无谓处理）
- 设置里可以关掉（`asr.denoise: false`）
- 进度条会如实报：「抗噪完成（248ms）：底噪 -29 → -46dB（降 17dB），说话段占比 48%，压掉 53Hz 的稳态嗡声。音频长度未变，时间轴照旧。」
- 抗噪记录随转写一起存进 `transcript.json` 的 `denoise` 字段（服务端白名单已放行），界面上会显示「已抗噪（底噪降 N dB）」

**踩过的坑（值得记住）**：这个「底噪降了多少」的数字一开始报出「-5dB」（不降反升），因为用逐帧频段能量的 10 分位当底噪，跟 RMS 不是一个量纲。改成在**时域**上量最低能量那 20% 帧的 RMS，并且必须在**任何处理之前**先量一次（后面全是原地改数据，等结尾再量「处理前」量到的已经是处理后的了）。

## 3. 缺陷②：不明字符 —— 真凶不是乱码，是繁体字

### 3.1 先推翻一个假设

最初的假设是「编码垃圾/乱码字符」。写脚本逐码位扫描三条真实记录后，这个假设被推翻了：

| 类别 | 出现次数 |
| --- | --- |
| 半角片假名 U+FF61–FF9F | **0** |
| 注音符号 U+3100–U+312F | **0** |
| emoji | **0** |
| 私用区字符 | **0** |
| CJK 兼容汉字 U+FA00–FAFF | **0** |
| 日文假名 / 谚文 | **0** |
| 全角括号（Whisper 自己加的注释） | 21 个（成对，有意义，保留） |

**非正文字符一个都没有。** 用户说的「不明字符」，实际是**繁简混排**（476 个繁体字，占全部 29860 字的 1.6%）加上 Whisper 的用词幻觉。

所以修法不是「拼命扩删字符正则」，而是「统一繁简」+「白名单兜底」。

### 3.2 繁→简表换代

旧表是手写的，实际只有 **195 条**，其中 **23 条是自己映射自己的废条目**（`呢:呢` `音:音` `源:源`……），真正干活的是 **169 条**。

拿它去处理真实记录，硬数字是这样的：

| 指标 | 数字 |
| --- | --- |
| OpenCC 认定的繁体形总数 | 2965 |
| 旧表认得且结果相同的 | **169（5.7%）** |
| 旧表漏掉的 | **2796（94.3%）** |
| **旧表在三条真实记录上实际能处理的繁体形** | **0 个** |
| 真实记录里实际存在的繁体形 | **476 个** |
| 新表能处理的 | **476 个（100%）** |

换表的代价：表从 0 行变成 19,083 字节。选择打成一个 `FLAT` 字符串（每 2 个字符一组 `[繁,简]`）+ 一个 `Map`，这是零依赖项目里最省事的做法。

**只收单字 1:1 映射**是刻意的：长度严格不变，所以逐段时间轴不会被破坏。

**只做字形转换、不做词汇转换**也是刻意的：「計程車」会变成「计程车」而不是「出租车」—— 字形转换不该改老师的用词。这一条在文件头注释里写清楚了。

### 3.3 清洗策略：从黑名单改成白名单

旧代码是「删掉这些 Unicode 区段里的字符」，漏一个区就漏一类字符。改成白名单：**只保留正文码位**，其余一律丢弃。

顺带修的三件事：

- 全角 ASCII 能救回来：「ＡＢＣ１２３」→「ABC123」（顺序必须在白名单之前）
- 康熙部首做 NFKC 归一：「⾔」→「言」（这是能救回正文的）
- 括号注释保留（记录里那 21 个全角括号是有意义的注记）

| 0e0eafc7（示例数据） | 879 字 / 繁体 0 | 879 字 / 0 |
| 1305e386（39 分钟） | 8364 字 / 繁体 **212** | 8364 字 / **0** |
| 62b4f73d（88 分钟） | 20617 字 / 繁体 **264** | 20593 字 / **0** |

汇总：繁→简 476 字、标点 96 处、折叠重复 24 字。88 分钟那条净减 24 字，来自折叠重复（`test-cleanup` 67/0）。

## 4. 顺带查出的关键 bug：大模型校对一直是坏的

### 4.1 校对从没跑起来过

两条真实转写的 `cleanedBy` 都是 `rule`，说明大模型校对从未生效。原因是 `127.0.0.1:8080` 上没有服务在跑 —— 代码和配置一直都是对的，只是服务没起来。

现在已拉起（命令和参数见 §9.1），实测校对可用。

### 4.2 跑起来之后撞上的真 bug：输出被截断成半截 JSON

第一次实跑 88 分钟那条（413 段）到第 5 块时崩了：

```
Error: 大模型校对输出不是合法 JSON，请重试
```

病根：校对要求模型**逐条回抄原文**，输出长度和输入同量级；而服务端转发时**从不传 `max_tokens`**，llama-server 默认 `-n_predict 512`，输出被硬截断成半截 JSON。

修的四处：

1. `public/llm.js` 的 `callLLM` 新增 `maxTokens` / `timeoutMs` 参数并透传
2. `server.mjs` 的 `POST /api/llm` 转发 `max_tokens`，超时改为可覆盖，并回传 `finish_reason`
3. 新增 `salvageJsonArray(text)`：用括号配对 + 字符串状态机，把被截断的 JSON 数组里**已经写完整的对象**抢救出来
4. 校对链路重写成**逐级降级**：块大小按 5000 → 2500 → 1250 → 800 逐级重试；**只有整个块的条目数一条不差才采纳**（少一条就是丢一段逐字稿）；全部失败则整块回退确定性清洗结果，**绝不缺段**

界面上的表现：万一某块降级了，会明确提示「第 2、3 块大模型没交出完整结果，已按基础清洗保留（未校对）」，而不是静默吞掉。

### 4.3 验证

`test-proofread-robust.mjs` **37/0**：用伪造的接口分别模拟「正常 / 输出被截断 / 裹着代码块 / 彻底不是 JSON / 模型报错 / 只回一半条目」六种情况，**每一种都做到段数守恒、无空段、时间戳原样保留**。

真实复跑 88 分钟那条 413 段：5/5 块全部完成，**没有降级块**；段数 413→413、时间戳未变、无空段；字数 20593→20552；耗时 436 秒。

核对音近错字：「鸡疫」0 次 /「基因」2 次；「设夺」0 次 /「设备」3 次。

**但要如实说**：只有 **20/413 段**被改动 —— 因为 whisper-small 转得太烂，大模型也改不动。这不是校对功能的问题，是**上游转写质量的问题**，也再次说明 §8.1 的重转写是必须做的。

## 5. 缺陷③：总结太浅 —— 提示词重写

### 5.1 病根

系统提示词写着「你只依据给定的材料整理，不编造内容」。**要求它不推理，它当然只能做缩句和换说法** —— 产出必然是「压缩版逐字稿」。

### 5.2 重写的思路

改成两段式：

- **MAP（分段）**：既要讲解也要摘录。允许补背景知识，但**必须带「（补充）」标记**；绝不允许编造老师没说过的结论、数字、例题
- **REDUCE / DIRECT（成稿）**：新增两个小节 —— **「理解脉络」**（3-8 条把知识连成一条线：要解决什么问题 → 前人做法卡在哪 → 这节课怎么绕过去 → 概念间关系）和 **「易错与易混」**（写成「X 和 Y 的区别在于…」）

短课走独立的 `DIRECT_PROMPT` / `DIRECT_SYSTEM`，因为它的输入是**原始逐字稿**（老师通常只讲了「是什么」没讲「为什么」），必须显式授权模型去解释和补背景；而 REDUCE 的输入是已经带讲解的分段要点。

### 5.3 调优过程中撞出来的四个坑（都值得记住）

1. **提示词里的圆括号说明会被模型当成正文抄进来**。A/B 测出「理解脉络」440 字看起来达标，打出来一看 300 多字是提示词本身（"2-3 句，说清内容与它在整节课里的位置"）。
   → 修法：所有写作要求从 `（…）` 改成 `［…］`，并在模板开头加一句「方括号里的话是给你的写作要求，不是要写的内容 —— 绝对不要把它们抄进输出」。
   → **教训：绝对不要在给模型的提示词里用圆括号写说明。**
   → **（2026-10-15 追加教训）这个修法不彻底**：老大第二轮实测发现，改成全角方括号后模型**照样把「［40 字以内，说清这节课的主线。］」「［这是整份笔记的核心…］」整段抄进笔记正文**（1305e386 的 note.json 实锤，`generator='offline'` 的旧笔记里就有）。所以光靠提示词请求是不够的，必须**代码兜底**：新增 `stripPromptLeaks(md)`，把「［…］」整段（可跨行）在渲染入口和保存前各过滤一次，见 §13。
2. **句式范例被当模板照抄**：要求写成「X 和 Y 的区别在于…」，模型直接输出了带字面占位符的句子。改用「概念甲」「概念乙」占位，并明写「不许把占位符写进输出」。
3. **整句照搬**：120 段样本上重合率 73.9%，模型把逐字稿整句搬进「课堂脉络与重点」。
   → 加硬性要求「除专业术语、公式、专有名词和数字外一律用自己的话重写，每条要点概括成 20-40 字」。
4. **阈值定标返工两次**：「理解脉络 ≥300 字」这条硬阈值在 2400 字的材料上根本达不到，只会得到一个恒红的测试 → 改成按材料长度定比例（`max(150, 材料字数 × 8%)`）；「新版产出更厚」也从硬断言降级为只提示（同一条记录三次跑出 4618 / 4937 / 6296 字，采样方差太大）。

## 6. 新增：连云端 API（给配置不行的电脑留一条路）

### 6.1 为什么要做

本机跑 `large-v3-turbo` 要 1GB 权重 + 显存/内存，7B 笔记模型常驻还要 6GB 左右显存。**买家未必有这个配置**：跑不动，或者跑起来整台电脑卡。所以除了「本地」，必须让人能选「云端」。

云端不是简单地「加个 API Key 输入框」——那样做出来的是个玩具，因为买家不知道去哪申请、填哪个地址、填哪个模型名。所以这一块做的是**一份带教程的服务商清单**。

### 6.2 做了什么

| 文件 | 作用 |
| --- | --- |
| `public/providers.js` | 服务商注册表：地址、模型卡片（档位/价格量级/一句代价）、默认模型、申请入口、分步 setup。前后端共用同一份（浏览器直接 import，服务端 import 后由 `GET /api/providers` 给出） |
| `public/api-tutorial.md` | 界面里点「怎么配」弹出来的教程，跟软件一起发出去，改文案不用动代码 |
| `docs/API接入教程.md` | 同一份教程的完整版，给买家自己看或打印 |
| `resolveAsrTarget()` / `resolveLlmTarget()` | 把「服务商 id + 用户填的覆盖项」解析成真正要请求的 `{url, model, apiKey, verbose}`，本地/云端在这一处分流 |

界面上的配套：

- **服务商只有四家**（本地 / 硅基流动 / OpenAI / 自定义），而且四家全部「转写 + 笔记」都能做。2026-10-21 从十一家收成四家：其中七家只能做一半（DeepSeek 只能笔记、Groq 只能转写），用户第一步就得先算「这家能不能干这个活」。收掉的那些全部收进「自定义」，它们是 OpenAI 兼容接口，填地址和模型名照样能用。
- **模型跟服务商绑定**：选完服务商，下面只显示这一家真正能调的模型。`test-providers.mjs` 里有一条断言专门查这个（硅基流动里不能出现 whisper-1、OpenAI 里不能出现 SenseVoiceSmall、两两服务商之间没有同名模型串台）。
- 模型是**卡片选择器**而不是下拉：每张卡写着档位徽章（免费 / 性价比 / 更强 / 自定义）+ 价格量级 + 一句代价，关键动作是「比较之后选一个」，下拉一次只露一项没法比。
- 「清掉已保存的 Key」按钮（空字符串在服务端表示「不修改」，没有这个按钮用户就删不掉自己粘错的 Key）

### 6.2.1 老配置自动迁移（2026-10-21）

服务商从十一家收成四家，老用户配置里可能还存着 `zhipu`、`deepseek` 这类 id。`server.mjs` 的 `migrateLegacyProviders()` 在 `loadConfig()` 读完盘之后立刻跑一次，分两类：

- **独立 OpenAI 兼容服务商**（deepseek / dashscope / zhipu / moonshot / groq / custom-llm）→ `'custom'`，`LEGACY_ENDPOINTS` / `LEGACY_MODELS` 里写死它们的官方地址和常用模型名，**只在用户没填过时补**，Key 完全不动。
- **本机那几条**（local-llm / ollama / lmstudio）→ `'local'`，它们本来就是 127.0.0.1 的接口。

每次迁移打一行 `[配置迁移] asr.provider: zhipu → custom` 到控制台，末了落盘一次。用户升级后不用重填 Key、不用重记地址。

### 6.3 顺手堵掉的三个坑

1. **Key 不进不出**。`GET /config` 只回 `hasApiKey: true/false`，从不回明文；`PUT` 的返回体里也没有。
2. **不允许请求体覆盖凭据**。原 `transcribeViaApi` 接受请求体里的 `opts.apiKey || a.apiKey`、`opts.model || a.model` —— 请求体是客户端说了算的，等于把用户保存的 Key 交出去（局域网里的恶意页面就能薅）。已改成只用服务端存的配置。
3. **写盘失败不再假装成功**。`saveConfig` 改成「先落盘、成了才改内存」，写不进去就回 500 并在界面上说清楚 —— 否则界面显示「已保存」、重启后又变回去，用户完全不知道发生过什么。

### 6.4 验证

`tests/test-providers.mjs` **62/0**（注册表与目标解析的纯逻辑，含「模型不会串台」和「卡片副标题不带括号」两条）、`tests/test-provider-migration.mjs` **41/0**（老配置自动迁移：收掉的服务商并进 custom / local、Key 和自填项不动、幂等）、`tests/test-cloud-e2e.mjs` **29/0**（真的起一个服务，走 HTTP 验配置读写、Key 保护、`checkOnly` 配置自检不会真发请求）、`tests/dom-app-test.mjs` **149/0**（跑真的 `public/app.js`，验下拉切换会填地址、模型卡片选择器、侧栏每行的「⋯ 编辑」入口带当前笔记设置、教程弹窗能出正文、清 Key 按钮真的发请求、**「重新生成笔记」/「AI 润色」两个按钮的文字与「转写后自动生成笔记」那条代码路径**）。

`checkOnly` 值得单说：上传一小时的录音之前，可以先让服务端**只检查配置、不发请求**，把「地址没填 / Key 没填 / 模型名不对」在花钱之前就告诉你。

## 7. 缺陷④：「转写一直在等待」—— 不是慢，是没有反馈；真凶是显存被本地大模型吃满

这一条是买家（老大）真实用的时候报上来的，比前三个缺陷更致命：**它在界面上看起来像死机**。

### 7.1 现象

界面上从第 1 秒到第 456 秒只有同一句「转写中 0:00 / 38:59 · 已等待 456 秒（正在下载或计算，别关窗口）」，**一个字都没变**，进度条纹丝不动。用户唯一的判断依据是「等」，而没有任何证据说明程序还活着。

### 7.2 为什么看着像死机：两处「没有反馈」

1. **模型命中缓存时，下载进度一条都不报**。`public/worker-asr.js` 的 `progress_callback` 只在真正走网络下载时报（判据是 `p.status === 'progress' && p.file`）。第二次以后模型已在缓存里，这条回调**永远不会触发**；而 ONNX 图编译 + 第一段推理这段时间 worker 也不发消息。
2. **界面只有「阶段名 + 等待秒数」，没有活着的迹象**。

采样证明程序确实在算：renderer 6 秒里新增 CPU 1.58 秒、GPU 进程 1.14 秒 —— 「在算，但不是死机」。

### 7.3 真凶：显存被本地大模型吃满，Whisper 上不了显卡

```
nvidia-smi --query-gpu=memory.used,memory.free,utilization.gpu --format=csv,noheader
→ 6779 MiB 已用 / 只剩 1121 MiB 空闲 / GPU 占用 7%
```

本地大模型（`llama-server`，约 4.3GB 的 Qwen2.5-7B）常驻占着显存。Whisper large-v3-turbo 的 q8 权重要 1.0–1.2GB，加上 WebGPU 的计算缓冲需要约 3–4GB 才稳；只剩 1.1GB 时它就在显存和内存之间来回倒腾 —— **表现就是 GPU 占用只有 7%、CPU 单核跑满、慢到看不出在动**。

这也解释了为什么「配置是对的、显卡也是好的，但就是慢」。

### 7.4 修法一：让程序会说话（心跳 + 分段 + ETA）

| 改动 | 文件 | 作用 |
| --- | --- | --- |
| 心跳 `beat(from, stage)` / `stopBeat()` | `public/worker-asr.js` | 每个阶段**立刻先发一句**，之后每秒一条带「已 N 秒」的进度；20 秒后补「这一阶段没有细进度，不是卡死」，60 秒后补「真的没卡死，但慢就是慢；嫌慢可以换更小的模型或改用云端接口」 |
| 第一段切到 ≤120 秒（`FIRST_SLICE_SEC`），之后每段 300 秒 | 同上 | 让**第一个字**早点出来，而不是等整条 |
| 每段报告「第 i/N 段（音频 mm:ss 起）/ 已完成 X / 用时 Y / 大约还要 Z」 | 同上 | ETA 只在跑完第一段后才给，**没算完绝不编数字** |
| 阶段徽章 + 百分比 + 细说明 + 无数值时的来回爬动画 | `public/index.html`、`public/app.css`、`public/app.js` | 分不清「在算」还是「卡死」的问题，从界面上根除 |
| 子阶段百分比换算成总进度（`overallPct`） | `public/app.js` | 避免「下载到 100% 又跌回 0%」这种更吓人的跳动 |

顺手修掉一个浪费：旧代码在 **WebGPU 初始化失败时会把 3 个模型源各试一遍**（本地代理 → hf-mirror → huggingface.co），三次都败在与「源」无关的设备错误上。现在拆成 `probeHosts()` + `buildOnce()`，并加 `isDeviceFailure()` 判断 —— 只有真的像设备错误才降级到 CPU(WASM)，且降级仍用同一个源；网络/模型名这类错误直接报出来，不假装降级。

### 7.5 修法二：转写前自动腾显存（老大选的方案）

新增 `const VRAM_NEED_MB = 2500;`（能稳稳跑起 turbo 的余量）与 `async function freeVramForTranscribe(gpu)`：

1. 显存不够**且**本地大模型在跑 → 说一句「显存只剩 X，正在自动停掉本地大模型腾地方…」
2. 调接口停掉它，然后轮询等显存回来（500ms × 30 次 = 最多 15 秒）
3. 腾够了 → 转写，并在**转写结束后自动把大模型拉回来**（`ensureLocalLLM()`，只拉一次）
4. 没腾够 → 照样往下走，但**明确警告可能退回 CPU 模式**，绝不谎报「已释放显存」

明确不碰的情况：显存充足、大模型没在跑、读不到显存读数、接口挂了（**转写该继续继续，不许被带崩**）。

实测效果：停掉本地大模型后 `freeMB` 从 **1121 MiB → 4843 MiB**，转写立刻从「磨洋工」变成正常在算。

### 7.6 验证

- `tests/test-vram-autofree.mjs` —— **28/0**。除了上面的正常路径，专门覆盖了「读不到显存时不许卡死」（不许空转 15 秒）、「接口挂了不许把转写带崩」、「stop 只发一次，不许连环杀」、「停了还是不够就必须说清楚，不许编好消息」。
- `tests/probe-worker-progress.mjs` —— 把 worker 源码里的 `await import(...transformers.min.js)` 换成 data: URL 假模块，用自制 `self`/`fetch` 接住，覆盖「模型下载中 / 模型已缓存（下载回调一条不报）/ WebGPU 失败回退 WASM」三种场景；断言含「转写百分比只增不减」。
- `tests/test-worker-device-fallback.mjs` —— **14/0**，断言「WebGPU 挂时管线只建 2 次、只探 1 次模型源、最终 device=wasm、降级文案含 WASM+慢」。
- 真浏览器（CDP 连真 Edge）确认：`#progress-stage` / `#progress-label` / `#progress-pct` 都在，`window.__LN__` 上 `checkGpu`、`runDiagnostics` 都是函数，真跑一条时进度条写出「第 1/8 段，已完成 0:00，用时 10 秒」。

### 7.7 显卡检测：按钮删了，能力保留在设置里

原来的界面有一个独立「显卡自检」按钮，但老大第二轮实测报「点了没反应、没啥用」，已**从主界面删除**（见 §13）。但「显卡到底能不能加速」这个问题本身是真实的，检测逻辑保留并修好了：

「显卡自检」原来只查 `'gpu' in navigator` —— **`navigator.gpu` 存在 ≠ 能用**（拿不到适配器时旧逻辑会报成「支持」）。现在真去 `requestAdapter({ powerPreference: 'high-performance' })` → 读 `adapter.info`（vendor/architecture）→ `requestDevice()`，失败时把原因原样带出来。

这个能力现在放在**设置 → ⑥ 环境自检**里（`checkGpu()` / `runDiagnostics()`），和 Node 版本、模型缓存等诊断项目一起跑，不再占用主界面。

### 7.9 三种跑法实测对比（同一台机器、同一条录音、同一份代码）

上面 §7.11 那个数字（120 秒音频、271.9 秒总耗时）是**第一轮**的；后来把「显卡加速到底有没有用」这件事查透了，又跑了两轮，结论**推翻**了「WebGPU 一定更快」的直觉。三轮全部是**绕过界面、直接调 `public/asr-local.js` 的真实链路**（`tests/bench-real-asr.mjs`，走真浏览器 CDP），测的都是 `新录音 1`（38:59，`onnx-community/whisper-large-v3-turbo`，`language: zh`，`denoise: true`）：

| 跑法 | 音频长度 | 转写本体 | 相对实时 | 输出质量 |
| --- | --- | --- | --- | --- |
| WebGPU + q8（量化） | 120 秒 | 526.8 秒 | **0.23×** | ❌ 成段乱码（英文/俄文/日文混着蹦） |
| CPU(WASM) + q8（量化） | 120 秒 | 约 300 秒 | **0.40×** | ✅ 中文可读 |
| WebGPU + fp16（半精度） | 30 秒 | 46.5 秒 | **0.64×** | ✅ 中文可读（最好的一档） |

（同表里的第一行 526.8 秒、第二行 0.40× 是此前两轮的实测；第三行是这一轮 30 秒音频的实测，`总耗时 51.2 秒` 里含 `整条音频解码 4.7 秒`。）

**由此得出一条必须记住的配置规则（已经写进代码）：**

- **`q8` 量化模型不能配 WebGPU。** 同一份 `encoder_model_quantized.onnx` / `decoder_model_merged_quantized.onnx`，走 WebGPU 会输出成段乱码，而且比 CPU 还慢（GPU 占用只有 13–22%）。这是 ONNX Runtime 的 WebGPU 后端对量化算子支持不成熟，不是参数没调对。
- 所以 `public/worker-asr.js` 里新加了一个 `pickDtype(model, device, override)`：**设备是 `webgpu` → `fp16`；设备是 `wasm` → `q8`**（`public/asr-local.js` 会把 `cfg.dtype` 传进 worker，`cfg.dtype` 也可以显式覆盖，用来复现上面那个坑）。
- 代价：`fp16` 权重单独一份，`encoder_model_fp16.onnx` 1215.3 MB + `decoder_model_merged_fp16.onnx` 328.3 MB ≈ **1.5 GB**（vs 量化版 615 MB + 419.6 MB ≈ 1.0 GB），第一次用要下载。`data/models` 目录现在两种都在，合计 3549.9 MB。

**为什么 WebGPU 也没快到哪去**：这台是 `NVIDIA GeForce RTX 5060 Laptop GPU`、显存 8151 MiB（见 §7.3），但 Whisper 的 ONNX 图里有大量小算子，WebGPU 每个算子的提交/拷贝开销把并行优势吃掉了 —— 所以「有独显 → 一定比 CPU 快」这个直觉在**这个模型 + 这个后端**上不成立。真正把速度拉开的是**精度**（q8↔fp16）和**要不要跟本地大模型抢显存**，不是显卡本身。

**给买家的实话**：想快，按性价比排序是 ① 转写前先别开本地大模型（已自动化，见 §7.5）→ ② 显卡够就开 WebGPU + fp16（约 1.6 倍于 CPU，代价 1.5 GB 下载）→ ③ 直接买云端接口（见 §6，最省事）。录 1 小时大概要转 1 小时上下，这是 `large-v3-turbo` 在 8GB 笔记本上的真实水平。

### 7.10 这一轮新增的两条验证（都能复现）

- `tests/test-vram-autofree.mjs` —— **28/0**（见 §7.6）。
- `tests/bench-real-asr.mjs` 现在支持 `--device` 和 `--dtype` 两个开关，可以逐格复现上表：`node tests/bench-real-asr.mjs --secs 30 --device webgpu --dtype fp16`。

### 7.11 速度实测（第一轮，保留备查）

在**显存已腾空**（空闲 6038 MiB）的状态下，用真浏览器跑 `新录音 1`（38:59）前 120 秒：

```
总耗时 271.9 秒，得到 7 段 / 435 字（只跑了前 120 秒音频）
```

### 9.3 长块为什么只能起出单词标题（`topicHeading` 的三条成因）

现象：`62b4f73d` 工程制图 9 个主题里有「机械」「作业」「投影」「垂直」四个单词标题，`2d1953e1` 7 个主题里也有「青年」「死亡」这些。大块（200+ 句）本该更容易出「A与B」这种双词标题，实际反而最难。

定位在 `public/summarize.js` 的 `topicHeading(blockSentences, globalKeywords, used)`（约 `:521-590`），三条成因叠加：

**① `need` 门限按块大小线性变严（主因）**
```js
const minCov = blockSentences.length >= 6 ? 2 : 1;
const need = Math.max(minCov, Math.round(blockSentences.length * 0.03));
```
`need` 是「一个候选词至少要在本块多少句里出现过」的下限，取块句数的 3%。块越大门槛越高，关键词覆盖数（cov）的分布却是长尾的，于是大块反而凑不出两个候选：

| 块 | 句数 | need | 过线的词 |
| --- | --- | --- | --- |
| 1 | 226 | 7 | 工程 cov=10、设计 cov=9、标准 cov=7（只有 3 个） |
| 2 | 228 | 7 | 机械 cov=7（唯一；投影 score=32.5 全场最高但 cov=2，过不了） |
| 3 | 291 | 9 | 作业 cov=10（唯一；考试 cov=4、手机 cov=3 全挡掉） |

**② `HEADING_BAD_START` 误杀专业名词**
```js
const HEADING_BAD_START = /^[一二三四五六七八九十百千万亿两几很多半这那什么怎么]/;
```
设计意图是挡住「第一」「第二」「一点」「很多」这类分条序号开头，但「**三角形**」首字是「三」，直接被当序号杀掉 —— 实测块 6 里 `三角形 cov=9` 是本块第二强的候选，块 7 里 `cov=7` 也是最强候选，全被挡。工科课里「三角形」「二维」「三视图」「两次投影」这类词全中招。

**③ 跨块 `used` 惩罚对「整节课都在讲的主题词」过度**
```js
if (used && used.has(t)) v *= 0.25;   // :539
```
`投影` 是工程制图整节课的核心词，第 5 块用过之后，第 6 块的权重从 0.254 掉到 0.071 —— 对「整门课围绕一个主题」的课程，这个 0.25 倍惩罚等于把它永久拉黑。

**已验证的修法与效果**：把 `HEADING_BAD_START` 改成只对两字词生效（三字以上的专业名词放行），另在 `topicHeading` 里把硬门限 `need` 改为**回退式选词**（先按 `need` 取，取不满 2 个就按 cov 降序放宽，但不低于 `minCov`）。改后 `62b4f73d` 的「直线」变成「**直线与三角形**」，`2d1953e1` 的标题也稳定下来，`test-pipeline.mjs`（24 项）、`test-note-header.mjs`（39 项）全绿。**`need` 的第三条（`used` 惩罚倍数）没动** —— 动它影响面太大，先留着。

## 12. 本报告是怎么生成的

正文源文件是 `docs/quality-report.md`（纯手写，所有数字都来自下面这些脚本的实际输出，没有估算）。

Word 版本（`docs/quality-report.docx`）由一个约 200 行的转换脚本从上面的 Markdown 生成，**不是**手工排版的。转换过程中撞到两个排版坑，记在这里免得下次重踩：

1. **行内代码不能改成等宽字体**。第一版把反引号里的内容设成 Consolas，在没有该字体的环境里 LibreOffice 会回退到 Courier，字符度量一变，整行就冲出页面右边界。
2. **加粗里面套的行内代码必须递归处理**。第一版只在外层切一次加粗标记，于是「加粗 + 里面套一个代码片段」这种嵌套里的反引号被外层整段吞掉，渲染出来是**字面带反引号**的正文。

另外：**判断「有没有冲出版面」必须看 PDF，不能看 PNG 预览**。直接用 LibreOffice 渲染出的 PNG 会给人一种「文字被右边界裁掉」的假象，转成 PDF 再看就完全正常。这一轮是白折腾的。

## 13. 老大第二轮实测后的五条改动

2026-10-15 老大试用后提了五条，全部改完并回归通过（`dom-app-test` 52/0、`api-test.ps1` 41/0、`test-docx` 11/0 等，见 §10）：

**① 思维导图改吃 AI 笔记结构（不再口语化）。** 病根：`app.js` 原来优先读 `note.data.outline`，而保存笔记时 `slimAnalysis(note)` 把**离线逐句摘录**存进了 `data`——离线引擎没有大模型，摘录就是口语原样，所以连 AI 笔记的导图也是口语。改法：`renderMindMapView` 先 `outlineFromMarkdown(note.markdown)`，从「## 课堂脉络与重点」的 `### 主题` + `- 要点` 生成书面语导图；markdown 没有结构才回退 `data.outline`。类名 `.mm-root`/`.mm-topic`/`.mm-point` 保留（`dom-app-test` 断言）。

> **2026-10-24 补充：这一版还不够。** 老大随后发现导图 tab 跟笔记 tab 的「课堂脉络与重点」**逐字相同**——因为上面只是把口语换成了书面语，内容仍是同一批要点句子，等于同一份东西摆了两遍。现在的做法是把叶子从「要点整句」换成 `public/note.js` 的 `topicLabels()` 抽的**短标签**（2~4 个，如「成绩构成 → 平时成绩 / 期末考试 / 出勤率 / 课堂表现」），抽不出就整个主题只留标题（宁空勿凑），`squeezeLabel()` 只在全空时摘一个 ≤10 字的短语兜底。同时 `.mm-t` 时间徽标从假的 `cursor:pointer` 改成真的 `<button>`，点击 `seek(t, true)` 跳转。`dom-app-test` 对应断言从「有 mm-point」扩到「每个标签 ≤14 字 / 没有标签与正文要点逐字相同 / 时间是 button」，项数 146 → 149。**抽不出标签的主题会显示一行灰字「这段没提炼出关键词」**（`.mm-none`）—— 留空白看着像没加载完。

**② 课程定位删掉。** 老大原话：「课程定位功能目前就是个摆设，去掉」。删了界面按钮 `#btn-course`、`doCourseDetect()`（`app.js`）与 `detectCourse()`（`llm.js`）。课程字段本身保留（可以手填）。

**③ 显卡自检按钮删掉。** 老大原话：「点了没反应…没啥用去掉」。删除 `#btn-gpu-check` 与其绑定；`checkGpu()` 与 `runDiagnostics()` 保留在 设置→⑥环境自检（`requestAdapter` 真检测逻辑原样保留，见 §7.7）。

**④ 导出只留 Word。** 原来四个导出按钮（MD/导图/SRT/TXT）下出来的文件老大打不开。现在只剩「导出 Word」+「复制笔记」。新建 `docx.mjs`（零依赖，手写 zip + OOXML，`test-docx` 11/0）：Markdown → .docx，逐字稿附录（`<details>`）不写进 Word；导出处理器默认 `kind=docx`，Content-Type `application/vnd.openxmlformats-officedocument.wordprocessingml.document`。**PDF 这一版不做**：零依赖手写 PDF 太重，LibreOffice 是开发机专属不能随产品发；docx 在 Word/WPS 里打开后可另存 PDF（界面文案已写明）。

**⑤ 提示词泄漏过滤。** 实锤：模型把提示词里的全角方括号写作要求整段抄进正文（note.json 里「［40 字以内，说清这节课的主线。］」「［这是整份笔记的核心…」）。光靠提示词改不掉（§5.3 坑 1），加代码兜底：`md.js` 新增 `stripPromptLeaks(md)` 把「［…］」整段（可跨行）删掉；渲染入口 + 生成保存前各过滤一次（`llm.js` 的 `linkifyTimestamps(stripPromptLeaks(markdown))`）。老笔记不改文件也能显示干净。

## 14. 可售性判断（实话）

### 14.1 能卖的部分

- 抗噪前端是**真本事**：纯 JS、零依赖、离线、248ms/54 秒、降 15.5dB 底噪而语音只损 0.7dB。这一条在同类工具里站得住，而且是**可验证的**（有 23 项回归测试）
- 繁简处理现在是对的（覆盖 100%，长度守恒）
- 大模型校对的降级链路做得扎实（六种坏输出下逐字稿一段不丢）
- 提示词从「缩句」升级到「讲解 + 梳理」，短课效果明显（重合率 70.9% → 56.1%）
- **本地 / 云端两条路都通了**，而且带教程 —— 配置差的电脑不必被劝退，也不必修好电脑才能用
- 界面按实测反馈改过一轮：思维导图吃 AI 结构、导出 Word 双击可开、提示词泄漏有代码兜底（§13）
- **双击就能跑，不需要装 Node、不需要装 Python、不需要联网激活**：`runtime\node.exe` 随包带（89.24 MB），安装包 25.8 MB，装完 90.6 MB
- **录音和模型缓存可以换盘**（设置 → ③ 存储位置），迁移只复制不删源 —— 这是给「C 盘只剩 20G」的学生准备的，也顺手解决了「模型缓存占 3.5G 又不能放 C 盘」这个真实抱怨

### 14.2 不能吹的部分

- **拼音首字母误识**（`BJR`→闭卷）的校对规则已加，但还没在真实数据上验证过（§8.5）。这是唯一一条「代码改了但没在真数据上确认生效」的
- **本地引擎不吐标点**：本地 Whisper 逐字稿每百字 0.47 个标点，云端 12.6~15.6（差 27 倍，§9.2）。本地路线能出字但读起来是「一长串没有停顿的汉字」，做逐字稿还行，直接当笔记素材交给大模型会掉质量。**这是「本地 vs 云端」取舍里唯一一处云端有硬质量优势的地方**
- **长块只能起出单词标题**：200+ 句的主题只能叫「机械」「作业」「垂直」，凑不出「A与B」（§9.3）。已修掉「三角形」被误杀的那一类，但 `need` 门限和 `used` 惩罚没动，长课目次仍偏素
- 长课「理解脉络」不随材料长度变长，短中稿方差还大（§5.4）——不算天花板，但也别吹「多长的课都吃得住」
- 云端那条路要求买家自己会申请 API Key（教程写得很细，但仍是门槛）
- 界面上还没有「第一次用该选哪个」的引导 —— 两条路的取舍写在 §8.4，但没写进界面
- **没有自动更新**：程序不会自己去查新版，用户得自己下载（§七之三 写了升级流程，但要手动）
- **没有错误上报**：崩溃了作者收不到任何信息

### 14.3 建议的卖法

卖「用你的录音产出讲义」这个**服务**（软件当作演示），或者**软件 + 一次代跑**。

理由是三条真实录音的对比已经说明：**同一条录音，小模型和 turbo 的产出差距是「读不通」和「能读」的区别**。这一点现在虽然可以靠云端 API 绕开，但让买家自己申请 Key、自己承担按量计费，转化率会掉；代跑一次把「读不通」变成「能读」，是最直接的价值证明。

这一条是判断，不是验证过的结论。

### 14.4 离「完整发售」还差什么（2026-10-20 盘点）

**已经齐了**：程序本体（33 项测试全绿，约 305 秒跑完）、安装包（Inno 6.7.3 打的，25.8 MB）、用户协议与隐私政策（19 项测试）、打赏入口（手机端实测修过遮挡）、换盘能力、质量回归基线（7 条录音、56 项断言）、服务商收成四家且模型跟服务商绑定（62 项断言 + 老配置迁移 41 项断言）、每条录音自己的笔记风格与提示词（含 AI 笔记的「重点条数」真的写进提示词，17 项断言）。

**还差的是「卖」这一侧的事，不是代码**：

| 差什么 | 为什么卡着 | 大概工作量 |
| --- | --- | --- |
| **定价与售卖页** | 现在只有打赏，没有价格、没有购买流程 | 要定价格、写卖点页、接支付（微信/支付宝个人收款或第三方） |
| **授权/激活** | 免费 + 打赏模式，**没有激活码机制**（原第⑥项试用/激活已按老大要求撤销） | 如果走「打赏」就不需要；要走「卖 license」就得重新做 |
| **自动更新通道** | 需要一个放安装包的公网地址（自己网站或 GitHub Releases） | 加一个「检查更新」按钮 + 下载 + 静默安装，代码量不大，**主要成本是那个地址** |
| **错误上报** | 完全没有 | 可选，加个匿名崩溃上报（要用户同意，隐私政策得同步） |
| **第一次用的引导** | 界面上没有「本地还是云端」的选择引导 | 一个首启向导，半天 |
| **真实用户试跑** | 只有作者自己的 7 条录音 | **这个没法用代码补**，至少找 3~5 个真实学生各录一节自己的课 |

**结论**：**代码层面离发售已经很近了**（差一个首启引导，可选加自动更新）；**卡的是运营层面**——定价、支付、发布地址、以及最关键的「真实用户试跑」。后者是唯一无法靠加班解决的。

如果明天就要卖，「软件 + 一次代跑」这条最稳：不需要激活码、不需要支付集成（一次一结）、不需要自动更新（代跑时顺手装最新版），而且代跑本身就是最好的质量证明。
